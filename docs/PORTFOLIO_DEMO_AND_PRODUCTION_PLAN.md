# План публикации Evergreen Dashboard для портфолио

## 1. Цель

Опубликовать Evergreen Dashboard так, чтобы посетитель портфолио мог:

1. одним кликом открыть интерактивное демо без регистрации;
2. проверить основные сценарии на безопасных тестовых данных;
3. при желании войти через Google и использовать полноценную версию со своими данными;
4. открыть исходный код и увидеть описание архитектуры проекта.

Целевой публичный адрес:

```text
https://dashboard.ilyaturcanportfolio.ru
```

Карточка на `https://ilyaturcanportfolio.ru` ведёт сразу на:

```text
https://dashboard.ilyaturcanportfolio.ru/demo
```

## 2. Целевые режимы

### 2.1. Демо

Маршрут `/demo` доступен без аккаунта и использует только демонстрационные данные.

В демо посетитель может:

- менять порядок, видимость, размер и параметры виджетов;
- добавлять, выполнять и восстанавливать демонстрационные рутины;
- запускать, ставить на паузу и завершать таймер;
- менять тему, часовой пояс и формат времени;
- просматривать демонстрационные погоду, календарь и новости;
- сбрасывать демо в начальное состояние;
- перейти к полной версии.

Демо не должно:

- создавать пользователя или сессию в production-базе;
- вызывать защищённые API;
- подключать Google Calendar, Telegram или Web Push;
- использовать общую учётную запись;
- содержать реальные персональные данные, OAuth-токены или секреты.

### 2.2. Полная версия

Маршруты `/dashboard` и `/settings/*` доступны после Google OAuth.

В полной версии источником истины являются API и PostgreSQL:

- настройки виджетов сохраняются на сервере;
- рутины и их выполнения сохраняются на сервере;
- таймер синхронизируется с API и worker;
- Google Calendar, Telegram, погода, новости и Web Push используют реальные интеграции;
- каждый запрос и изменение ограничены текущим пользователем.

## 3. Архитектурные решения

1. Не использовать общий demo-аккаунт: посетители не должны видеть или перезаписывать действия друг друга.
2. Не добавлять публичный demo-endpoint в Express: демонстрационные данные и действия остаются во frontend.
3. Не смешивать проверки `isDemo` с доменной логикой полной версии. Создать отдельную demo-композицию поверх общих UI-компонентов.
4. Не импортировать backend-код во frontend. Общие DTO и схемы остаются в `packages/contracts`.
5. Полная версия работает через относительные `/api/v1/*`; Next.js и reverse proxy направляют запросы в API.
6. Секреты, OAuth credentials и session token никогда не попадают в клиентский bundle или `localStorage`.
7. Для навигации использовать ссылки, для действий — кнопки. Все действия доступны с клавиатуры и имеют видимый focus.
8. Все изображения карточки портфолио получают явные `width`, `height` и содержательный `alt`, чтобы избежать CLS и сохранить доступность.

## 7. Этап 3 — подключить полную версию к существующим API

Все мутации используют contracts, `X-CSRF-Token`, обработку timeout/abort и понятный rollback оптимистичного UI.

### 7.1. Настройки виджетов

Использовать:

```text
GET   /api/v1/widgets/preferences
PATCH /api/v1/widgets/preferences
```

- [ ] Загружать серверные настройки для авторизованного пользователя.
- [ ] Сохранять порядок, размер, видимость и параметры через API.
- [ ] Использовать локальное состояние только для optimistic UI.
- [ ] При ошибке восстанавливать последнюю подтверждённую сервером версию.
- [ ] Не заменять серверные настройки данными из demo.

### 7.2. Рутины

Использовать:

```text
GET    /api/v1/routines
GET    /api/v1/routine-rules
POST   /api/v1/routine-rules
PATCH  /api/v1/routine-rules/:id
DELETE /api/v1/routine-rules/:id
POST   /api/v1/routine-rules/:id/restore
PATCH  /api/v1/routine-occurrences/:id
```

- [ ] Заменить локальное добавление и toggle на API-мутации.
- [ ] Поддержать optimistic update только с rollback.
- [ ] Передавать `Idempotency-Key` для повторяемых POST.
- [ ] Синхронизировать Dashboard и страницу управления рутинами.
- [ ] Проверить смену дня и часового пояса.

### 7.3. Таймер

Использовать:

```text
GET   /api/v1/timers/current
GET   /api/v1/timers
POST  /api/v1/timers
PATCH /api/v1/timers/:id
```

- [ ] Сделать серверный `endsAt` источником истины.
- [ ] Оставить браузерный interval только для отображения обратного отсчёта.
- [ ] Восстанавливать активную сессию после reload и входа с другого устройства.
- [ ] Обработать конкурирующее изменение таймера в двух вкладках.
- [ ] Проверить постановку worker-задачи завершения.

### 7.4. Уведомления

Использовать:

```text
GET    /api/v1/notifications/preferences
PATCH  /api/v1/notifications/preferences
GET    /api/v1/notifications
POST   /api/v1/push/subscriptions
DELETE /api/v1/push/subscriptions/:id
```

- [ ] Сохранять Web Push subscription только после явного разрешения пользователя.
- [ ] Удалять или отзывать subscription при отключении.
- [ ] Синхронизировать настройки каналов с сервером.
- [ ] Не записывать push endpoint или ключи в логи.

Критерий завершения: после reload и входа на другом устройстве серверные функции сохраняют согласованное состояние.

## 10. Этап 6 — подготовить production-инфраструктуру

Целевая схема остаётся совместимой с текущей архитектурой:

```text
Internet
  -> TLS reverse proxy
      -> web
      -> /api/v1/* -> api
  -> worker
api + worker
  -> managed Neon PostgreSQL
```

## 16. Definition of Done

Работа завершена, когда одновременно выполнены все условия:

- `/demo` доступен без регистрации и не зависит от API;
- демо интерактивно и использует только безопасные тестовые данные;
- `/dashboard` и `/settings/*` требуют серверную сессию;
- полная версия сохраняет виджеты, рутины и таймер через API;
- реальные интеграции работают независимо и безопасно отключаются;
- новый внешний Google-пользователь может войти;
- production работает только по HTTPS;
- API и worker используют managed PostgreSQL;
- миграции, health checks, backup и rollback задокументированы и проверены;
- критические unit, integration, component и E2E-тесты проходят;
- security review не содержит открытых high/critical замечаний;
- карточка на `ilyaturcanportfolio.ru` открывает `/demo`;
- из демо очевидно доступен переход к полной версии и исходному коду.
